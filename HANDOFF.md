# Handoff — Gorne MD EMR

Read this first in any new session working on this project. It exists because this project was scaffolded from a Claude Code session rooted at a *different* directory (`~/Sites/jazgornemd.com/jazgornemd-theme`), so file edits were happening one directory over from the session root — annoying enough that we're picking this up fresh, rooted directly at `~/Sites/gorne-md-emr`, from here on.

## What this project is

A ground-up replacement for a WordPress-based clinic EMR (`jazgornemd-theme`, at `~/Sites/jazgornemd.com/jazgornemd-theme`) built for a small Philippine medical practice (Dr. Gorne — adult and pediatric patients, distinguished by which doctor account is logged in). The old system: patients, diagnoses, prescriptions ("resitas"), medical certificates, and vital signs stored as WordPress ACF postmeta, gated behind a login wall, with real security bugs (two AJAX endpoints leaked clinical data to unauthenticated requests) and fragile design (a `doctor` role referenced everywhere but never defined in code, patient adult/pedia segmentation hardcoded to doctor email addresses).

A full audit of that old system was published as an artifact: **"JazGorneMD Chart Review"** (`https://claude.ai/code/artifact/28e8b370-8de4-468c-9b8d-eba747998bd1`) — it documents every field, workflow, role, and security finding of the old app, plus a "Exporting to a new system" section covering WordPress data migration (deferred to a later phase — not part of this build).

## The full architecture plan

**Read `/Users/eyorsogood/.claude/plans/lets-check-and-review-graceful-rabin.md` in full before continuing implementation.** That plan file (outside this repo, on the machine this was built on) is the source of truth for: the Supabase schema and RLS design, the auth/role model, signature capture design, the PDF generation approach and why it was chosen over alternatives, the "seamless issuing" UX flow, and the full phased roadmap. What follows here is only a progress checkpoint, not a replacement for that plan.

Key decisions already made (do not re-litigate these without a good reason):
- **Separate, dedicated project** — intentionally not merged into the user's other, larger `clinic-management` monorepo (different clinic, has appointments/visits/labs/billing/inventory/Loyverse POS, no prescriptions/med-cert features of its own).
- **Scope**: patients, vitals, diagnosis, prescriptions, medcerts only. No appointments, billing, inventory, or visit/queue/encounter concept. Prescriptions/medcerts stand alone directly against the patient chart.
- **Roles: `admin` and `doctor` only** (no third "staff" role). Admin = non-clinical superuser (data management, account provisioning). Doctor = clinical role, owns a signature, issues prescriptions/medcerts under their own name. Both can view/manage patients, vitals, diagnosis; only `doctor` can create new prescriptions/medcerts.
- **Print target**: half-letter Rx pad, placeholder 139.7mm × 215.9mm in `lib/print/page-size.ts` — **must be confirmed against the actual physical pad with a ruler before launch**, that file is the only place the dimension is defined.
- **PDF approach**: `puppeteer-core` + `@sparticuz/chromium` in a Vercel Node.js serverless function, sharing one HTML/CSS template with the browser-print route (not yet implemented — this is Phase 3, and its own named risk to spike early: confirm it fits Vercel's function size/cold-start limits before building the rest of Phase 3 around it).
- **Signature**: `react-signature-canvas`, captured once per doctor, stored in Supabase Storage, pinned by `signature_id` on each document at issue time (never re-resolved) so reprints stay faithful to what was signed at the time.
- **Cloud infra**: the user creates the Vercel project and Supabase project themselves — fresh instances, no reuse of any existing project. Nothing in this codebase provisions cloud accounts.
- Next.js scaffolded at **v16** (latest, not v15) deliberately — the user asked for "today's tech standards," and version parity with the sibling `clinic-management` project wasn't judged worth sacrificing that for. `AGENTS.md`/`CLAUDE.md`'s `@AGENTS.md` import is auto-generated by Next 16's own tooling (`next dev`) warning that this Next.js version has breaking changes vs. older training data — heed it, don't delete it.

## What's already built

### Phase 0 — Scaffold & Auth (done)

- Next.js 16 App Router + TypeScript + Tailwind v4, via `create-next-app`.
- shadcn/ui initialized (`base-nova` preset, built on `@base-ui/react` — **not Radix**: no `asChild`, components take a `render` prop instead, e.g. `<Button render={<Link href="..." />}>`; a `Button` rendered as a non-`<button>` needs `nativeButton={false}` or it logs a console warning). Installed components: `button, input, label, textarea, select, checkbox, card, table, tabs, badge, dialog, dropdown-menu, separator, avatar, sonner, sheet`. No `form.tsx` wrapper — forms are built directly with React Hook Form (`register`/`Controller`) plus these primitives.
- Installed: `@supabase/supabase-js`, `@supabase/ssr`, `@tanstack/react-query`, `react-hook-form`, `@hookform/resolvers`, `zod`, `react-signature-canvas`.
- `lib/db/client.ts` — `getSupabaseClient('anon' | 'service')`. `lib/db/browser-client.ts` — browser-side client for client components.
- `lib/auth/session.ts` — `requireUser()` (resolves session + `profiles` row via service-role read), `requireRole(profile, roles[])`, `AuthError`.
- `proxy.ts` — redirects unauthenticated requests to `/login` and authenticated requests away from `/login`, via `@supabase/ssr` on Next 16's `proxy` convention (not `middleware.ts` — deleted by the codemod, don't reintroduce it). **Note**: proxy does not handle `/` itself — `app/page.tsx` is a small server component that calls `requireUser()` and redirects to `/patients` or `/login`; it was left as the create-next-app boilerplate for a while and silently never redirected authenticated users, so don't assume proxy covers every route.
- `lib/print/page-size.ts` — physical page-size constant for Phase 3, **not yet confirmed against the real Rx pad**.
- `supabase/migrations/0001_init.sql` — the full schema for all phases in one migration: `profiles`, `doctor_profiles`, `doctor_signatures`, `patients`, `patient_lab_results`, `vital_signs`, `diagnoses`, `prescriptions`, `medcerts`, `audit_log`, storage buckets (`signatures`, `patient-photos`, `lab-results`, all private), full RLS. **Applied and confirmed working** against the live Supabase project. One fix already baked in: `current_profile_role()` is a `language sql` function and must be defined *after* the `profiles` table it queries — Postgres validates a SQL function body's referenced relations at `CREATE FUNCTION` time, so the original ordering (helper function before the table) failed on first real apply with `relation "public.profiles" does not exist`. If you ever split this into more migrations, keep that ordering constraint in mind.
- `lib/validation/admin.ts` + `app/api/admin/users/route.ts` — admin-only account provisioning (`auth.users` + `profiles` in one request, rolls back the auth user if the profile insert fails, writes `audit_log`).
- `app/(auth)/login/page.tsx`, `app/(app)/layout.tsx` (role-scoped nav shell via `components/layout/AppNav.tsx`, a client component so nav can highlight the active route), `app/(app)/admin/users/page.tsx` + `components/admin/CreateUserForm.tsx`.
- `components/layout/UserMenu.tsx` — avatar + dropdown with **Sign out** (`supabase.auth.signOut()` then redirect to `/login`). This didn't exist for a while after Phase 0 — there was no way to log out at all until it surfaced while writing an automated two-account test. Wired into the app shell's header.
- Repo connected to `git@github.com:rilustrisimo/jazmd-emr.git` as `origin`, `main` pushed and tracked. **Vercel project connection has not been verified in any session** — confirm a push to `main` actually auto-deploys before relying on that exit criterion.
- **Theme**: `app/globals.css` carries the brand palette (`#0165FC` primary, `#242424`/`#484848` text, `#EAECF0` tint, light+dark tokens) and Inter (`app/layout.tsx`) in place of the shadcn defaults/Geist. `--font-sans` was previously self-referential (`var(--font-sans): var(--font-sans)`) and silently never applied the loaded font — fixed. `components/ui/card.tsx` has a shadow added on top of the shadcn default. Visual language across the app: rounded-xl cards, pill (`rounded-full`) primary buttons, tinted-icon-circle empty states (`bg-primary/10 text-primary`).

First real admin account is provisioned (Jasmin Gorne) directly in Supabase, as designed (no bootstrap UI for the very first account).

### Phase 1 — Patient chart CRUD (done)

- `lib/validation/patients.ts` — `patientSchema`/`labResultSchema`. Exports **two** types from one schema: `PatientFormValues` (`z.input`, what the form holds pre-transform) and `PatientInput` (`z.output`, what gets submitted post-transform) — the empty-string-to-null transforms on optional fields make these genuinely different shapes, and treating them as one (`z.infer`) breaks TypeScript against `zodResolver`. `PatientForm.tsx` uses RHF's 3-generic `useForm<TFieldValues, TContext, TTransformedValues>` to keep both ends typed correctly — reach for this pattern again for any future form with optional/transformed fields (vitals, diagnoses, prescriptions).
- `lib/patients/age.ts` (`computeAge`, honoring `age_override` same as the plan's escape hatch), `get-patient.ts`, `get-lab-results.ts`, `types.ts` (`PatientRecord` + DB-row↔form-input mapping). `lib/storage/signed-url.ts` — every patient photo / lab-result file the UI shows goes through a short-lived signed URL minted server-side; buckets stay private, never a public bucket URL.
- `app/api/patients/route.ts` (list defaults to the logged-in doctor's `doctor_patient_scope`, `?type=all|adult|pedia` overrides; create), `app/api/patients/[id]/route.ts` (get/update/soft-delete — delete is `requireRole(['admin'])` in the route *and* backstopped by the DB trigger), `app/api/patients/[id]/photo/route.ts`, `app/api/patients/[id]/lab-results/route.ts`, `app/api/lab-results/[id]/route.ts` (admin-only delete).
- `components/patients/*` (`PatientsList` search+table, `PatientForm`/`PatientEditForm` shared form, `PatientPhotoUpload`, `LabResults`, `PatientDeleteButton` confirmation dialog) and `app/(app)/patients/{page,new,[patientId],[patientId]/edit}.tsx`. The chart page's tabs include placeholder panels for Vitals/Diagnosis (Phase 2) and Prescriptions/Med certs (Phase 3) — don't build those out until their phase.

**Verified** with an automated Playwright run against the live dev server using a real (throwaway, fully torn down afterward) doctor + admin account pair: doctor creates a patient and sees it in their scoped list; a lab result persists; editing works; admin sees the same patient with no scope restriction and has a delete control the doctor correctly does not; soft-delete removes it from lists. This is the pattern to repeat for Phase 2/3 verification — spin up throwaway accounts via the service-role key (`auth/v1/admin/users`), test, then delete them (note: deleting an auth user with `audit_log` rows referencing it fails on the FK — clear those rows first if you need to clean up a throwaway account, real accounts should never need this).
