# Handoff — Gorne MD EMR

Read this first in any new session working on this project. It exists because this project was scaffolded from a Claude Code session rooted at a *different* directory (`~/Sites/jazgornemd.com/jazgornemd-theme`), so file edits were happening one directory over from the session root — annoying enough that we're picking this up fresh, rooted directly at `~/Sites/gorne-md-emr`, from here on.

## What this project is

A ground-up replacement for a WordPress-based clinic EMR (`jazgornemd-theme`, at `~/Sites/jazgornemd.com/jazgornemd-theme`) built for a small Philippine medical practice (Dr. Gorne — adult and pediatric patients, distinguished by which doctor account is logged in). The old system: patients, diagnoses, prescriptions ("resitas"), medical certificates, and vital signs stored as WordPress ACF postmeta, gated behind a login wall, with real security bugs (two AJAX endpoints leaked clinical data to unauthenticated requests) and fragile design (a `doctor` role referenced everywhere but never defined in code, patient adult/pedia segmentation hardcoded to doctor email addresses).

A full audit of that old system was published as an artifact: **"JazGorneMD Chart Review"** (`https://claude.ai/code/artifact/28e8b370-8de4-468c-9b8d-eba747998bd1`) — it documents every field, workflow, role, and security finding of the old app, plus a "Exporting to a new system" section covering WordPress data migration (deferred to a later phase — not part of this build).

## The full architecture plan

**Read `/Users/eyorsogood/.claude/plans/lets-check-and-review-graceful-rabin.md` in full before continuing implementation.** That plan file (outside this repo, on the machine this was built on) is the source of truth for: the Supabase schema and RLS design, the auth/role model, signature capture design, the PDF generation approach and why it was chosen over alternatives, the "seamless issuing" UX flow, and the full phased roadmap. What follows here is only a progress checkpoint, not a replacement for that plan.

Key decisions already made (do not re-litigate these without a good reason):
- **Separate, dedicated project** — intentionally not merged into the user's other, larger `clinic-management` monorepo (different clinic, has appointments/visits/labs/billing/inventory/Loyverse POS, no prescriptions/med-cert features of its own).
- **Scope**: patients, vitals, diagnosis, prescriptions, medcerts only. No appointments, billing, inventory, or visit/queue/encounter concept. Prescriptions/medcerts stand alone directly against the patient chart.
- **Roles: `admin` and `doctor` only** (no third "staff" role). Admin = non-clinical superuser (data management, account provisioning). Doctor = clinical role, owns a signature, issues prescriptions/medcerts under their own name. Both can view/manage patients, vitals, diagnosis; only `doctor` can create new prescriptions/medcerts.
- **Print target**: half-letter Rx pad, placeholder 139.7mm × 215.9mm in `lib/print/page-size.ts` — **must be confirmed against the actual physical pad with a ruler before launch**, that file is the only place the dimension is defined.
- **PDF approach**: `puppeteer-core` + `@sparticuz/chromium` in a Vercel Node.js serverless function, sharing one HTML/CSS template with the browser-print route. Implemented in Phase 3 (`lib/pdf/render.ts`) and **confirmed working on the real Vercel deployment** — see Phase 3's section below for the two real bugs this took to fix, most importantly: **production must build with `next build --webpack`, not Turbopack** (`package.json`'s `build` script) — do not "clean up" that flag back to plain `next build`, it will silently break PDF generation again.
- **Signature**: `react-signature-canvas`, captured once per doctor, stored in Supabase Storage, pinned by `signature_id` on each document at issue time (never re-resolved) so reprints stay faithful to what was signed at the time.
- **Cloud infra**: the user creates the Vercel project and Supabase project themselves — fresh instances, no reuse of any existing project. Nothing in this codebase provisions cloud accounts.
- Next.js scaffolded at **v16** (latest, not v15) deliberately — the user asked for "today's tech standards," and version parity with the sibling `clinic-management` project wasn't judged worth sacrificing that for. `AGENTS.md`/`CLAUDE.md`'s `@AGENTS.md` import is auto-generated by Next 16's own tooling (`next dev`) warning that this Next.js version has breaking changes vs. older training data — heed it, don't delete it.

### Phase 1 — Patient chart CRUD (done)

- `lib/validation/patients.ts` — `patientSchema`/`labResultSchema`. - `app/api/patients/route.ts` (list defaults to the logged-in doctor's `doctor_patient_scope`, `?type=all|adult|pedia` overrides; create), `app/api/patients/[id]/route.ts` (get/update/soft-delete — delete is `requireRole(['admin'])` in the route *and* backstopped by the DB trigger), `app/api/patients/[id]/photo/route.ts`, `app/api/patients/[id]/lab-results/route.ts`, `app/api/lab-results/[id]/route.ts` (admin-only delete).

**Verified** with an automated Playwright run against the live dev server using a real (throwaway, fully torn down afterward) doctor + admin account pair: doctor creates a patient and sees it in their scoped list; a lab result persists; editing works; admin sees the same patient with no scope restriction and has a delete control the doctor correctly does not; soft-delete removes it from lists. - **Bug found and fixed while building void**: `supabase/migrations/0002_fix_void_trigger_service_role_writes.sql`. The original void-guard triggers on `prescriptions`/`medcerts` check `current_profile_role()`, which resolves via `auth.uid()` — null for service-role-authenticated writes, which is how every write from this app happens. The original trigger treated null as "not authorized" and unconditionally rejected every void attempt (confirmed against the live DB before fixing it: every void attempt returned `"Not permitted to void this prescription"`). Fixed to only enforce the check when a real session actually resolved a role — mirrors how the patients soft-delete trigger already no-ops on null, just making it deliberate here instead of an accident of that trigger's negated condition. **Applied to the live Supabase project and confirmed working** — voided a real seeded prescription successfully.
- `lib/print/document-styles.ts` + `lib/print/render-document-html.ts` — the shared template, deliberately plain HTML-string generation (not a React component, despite the plan's file list naming `components/print/PrescriptionDocument.tsx`) so the *exact same string* feeds both Puppeteer's `page.setContent()` and the browser-print page's `dangerouslySetInnerHTML` — zero risk of the two drifting, which was the plan's stated reason for sharing a template in the first place. `lib/documents/get-print-data.ts` fetches and shapes the joined patient/doctor/signature data, inlining the signature as a base64 data URI (never a signed/public URL, per the plan).
- `lib/pdf/render.ts` — `puppeteer-core` + `@sparticuz/chromium` when `process.env.VERCEL` is set (true on every Vercel deployment including previews), full `puppeteer` (new devDependency) otherwise as a local stand-in only, never bundled into production. Launch args/`headless` value match `@sparticuz/chromium`'s own documented usage (`puppeteerCore.defaultArgs({ args: chromium.args, headless: 'shell' })`).
- `app/(app)/patients/[patientId]/{prescriptions,medcerts}/[id]/print/page.tsx` (browser-print; the app shell nav is hidden via `print:hidden` on the header in `app/(app)/layout.tsx`, confirmed working with `page.emulateMedia('print')`) and `app/api/{prescriptions,medcerts}/[id]/pdf/route.ts` (`runtime = 'nodejs'`, `maxDuration = 60`).
- `components/records/{Prescriptions,Medcerts}.tsx` — issue form, list, print/download/void actions, wired into the chart page's last two tabs.

**The named risk — two real bugs found and fixed, only discoverable by testing against the actual Vercel deployment (the earlier "verified locally" pass could not have caught either of these):**

1. **`next.config.ts` needed `serverExternalPackages: ["@sparticuz/chromium", "puppeteer-core"]`.** Both packages resolve their own binary/asset paths at runtime relative to their package location in `node_modules`; without this, Next's bundler rewrites those paths while bundling and breaks them silently.
2. **The real blocker: production must build with `next build --webpack`, not Turbopack.** `@sparticuz/chromium`'s compressed Chromium binary (`node_modules/@sparticuz/chromium/bin/*.br`) is loaded dynamically at runtime, not via a `require()` path static analysis can discover on its own — it needs an explicit `outputFileTracingIncludes` entry (already in `next.config.ts`) to get bundled into the deployed function. **But Next.js 16.3.5's own build source (`next/dist/build/index.js`) gates its entire trace-collection step behind `bundler !== Bundler.Turbopack`** — `outputFileTracingIncludes` is silently a complete no-op under Turbopack, which is this project's default bundler. Confirmed directly: a Turbopack build produces *no* `.nft.json` trace file for the PDF routes at all; `next build --webpack` produces one that correctly lists every `@sparticuz/chromium/bin/*.br` file. Without this, every PDF request failed in ~4s with `"The input directory .../node_modules/@sparticuz/chromium/bin does not exist"` — three redeployments in a row looked identical because the fix genuinely had zero effect until the bundler itself changed. `package.json`'s `"build"` script is now `"next build --webpack"`; `"dev"` stays on Turbopack for local dev speed, since this limitation is specific to the trace-collection step, not Turbopack generally. **If you ever see this exact error again** (e.g. after a Next.js upgrade that might lift this Turbopack limitation, or if someone "cleans up" the build script back to plain `next build`), check this first before anything else.

Diagnosis method worth repeating for any future "works locally, fails on Vercel" issue: temporarily added a `debug` field to the PDF route's catch block echoing `error.message`/`error.stack` in the JSON response (committed, tested, then reverted once root-caused) — there is no other way to see a Vercel function's real runtime error without dashboard/CLI access to that account, which this session didn't have.

**Verified, both locally and on the real Vercel deployment**: doctor-profile-then-signature gating; both document types issue with the signature correctly pinned; both PDF endpoints confirmed by reading the actual generated PDF bytes on `https://jazmd-emr.vercel.app` itself — letterhead, patient info, content, and the real captured signature all present and correctly positioned on a half-letter page, generated in ~6s; the browser-print route matches the PDF exactly (same template function); print media correctly hides the app chrome; void works end to end.

**Still open**: physically measure the Rx pad against `lib/print/page-size.ts`'s placeholder (139.7mm × 215.9mm) — the only remaining Phase 3 sign-off item, and it needs the user, not more code.

### Password reset (done, outside the phased plan — added when the user got locked out)

- `app/(auth)/forgot-password/page.tsx` (email entry, `supabase.auth.resetPasswordForEmail()`, always shows the same "check your inbox" state regardless of whether the email is registered — avoids leaking which clinic staff emails exist) and `app/(auth)/reset-password/page.tsx` (sets the new password after the emailed link). Both added to `proxy.ts`'s `PUBLIC_PATHS`. A "Forgot password?" link was added to `app/(auth)/login/page.tsx`.
- **Real bug found and fixed while verifying this**: `@supabase/ssr`'s `createBrowserClient` hardcodes `flowType: 'pkce'`, but this project's Supabase Auth is configured to send recovery emails using the **implicit** flow (`#access_token=...&refresh_token=...` in the URL fragment, confirmed by generating and following a real recovery link). A PKCE-configured client does not auto-detect an implicit-flow fragment — `detectSessionInUrl` silently does nothing, so the reset-password page would show "invalid or expired link" for every real recovery email, permanently. Fixed in `reset-password/page.tsx` by parsing `window.location.hash` manually and calling `supabase.auth.setSession({ access_token, refresh_token })` directly, with a `getSession()` fallback for a PKCE-style (`?code=`) link in case the project's Auth flow-type setting ever changes. If you ever add magic-link sign-in or any other Supabase email-link flow, this same mismatch will bite you there too — either fix it the same way (parse the fragment, call `setSession`/`exchangeCodeForSession` explicitly) or change the project's Auth flow-type setting in the Supabase dashboard to match `@supabase/ssr`'s PKCE expectation.
- **Verified end to end against the live Supabase project**: generated a real recovery link via the admin API (`POST /auth/v1/admin/generate_link`, which returns the link directly — no need for actual email delivery, useful for testing this without an SMTP provider configured), drove it through both pages with Playwright, confirmed the new password actually works for a fresh login afterward. Also verified the always-succeeds forgot-password messaging and the invalid-link state with no token present.
- The user's real admin account (Jasmin Gorne) password was reset directly via the service-role key during this work, at their explicit request (they were locked out) — a one-off action, not part of the code change.

### Supabase keep-alive cron (done)

Supabase pauses free-tier projects after ~7 days of no API activity. `vercel.json` schedules a daily Vercel Cron hit against `app/api/cron/keep-alive/route.ts`, which does a trivial `profiles` read — enough to count as activity. Optionally protected by a `CRON_SECRET` bearer check (Vercel sends this automatically if that env var is set on the Vercel project; not set anywhere yet, so the endpoint is currently open to anyone who finds the URL — low risk, since it only performs a harmless read, but set `CRON_SECRET` in Vercel's env vars if you want it locked down).

**Real bug caught before shipping**: `proxy.ts` redirects every unauthenticated request to `/login` — Vercel's cron invocation carries no Supabase session cookie, so without adding `/api/cron` to `PUBLIC_PATHS`, the cron hit would have silently 307'd to `/login` forever, never once reaching Supabase, completely defeating the point. Caught by testing the route against a local dev server before pushing (status came back 307, not 200), not by inspection — the same discipline worth applying to any future route that's meant to be hit by something other than a logged-in browser.

Also discovered while adding `CRON_SECRET` to `.env.example`: that file had **never actually been committed to this repo** — the `.env*` gitignore pattern (left over from `create-next-app`'s default) silently blocked it from every prior commit, despite containing no secrets, just variable names and placeholder values. Force-added it now (`git add -f`). If you add more env vars in the future, remember `.env.example` needs `-f` to actually get staged.

Verified both locally (unauthenticated success when `CRON_SECRET` unset; correct 401/200 behavior when it is set) and against the live Vercel deployment (`https://jazmd-emr.vercel.app/api/cron/keep-alive` returns `{"ok":true,"pingedAt":"..."}`).

- **Real nuance found while verifying this, worth understanding before adding more navigation-triggering UI**: `loading.tsx` does **not** reliably show for client-side `router.push()`/`<Link>` navigations within an already-mounted session — React wraps these in a transition and deliberately keeps the current page visible with no fallback while it's pending (that's intentional React behavior, not a bug, meant to avoid flashing a spinner for fast transitions). It only reliably fires for a genuinely fresh/hard page load. Confirmed by testing the patient-list-to-chart transition under throttled network on the live deployment: zero visual feedback for 500ms+ despite the navigation still being in flight. Fixed specifically for `components/patients/PatientsList.tsx`'s row click (the app's most-used list→detail transition) using React's `useTransition` for an explicit `isPending` flag instead of relying on the Suspense fallback — the clicked row shows a spinner, other rows dim and stop accepting clicks. **This same pattern has not been applied to every other `Link`/`router.push()` in the app** (e.g. the chart page's Edit button, nav links) — those still rely on `loading.tsx` alone, which is fine for a fresh page load but may show nothing for a same-session soft navigation on a slow connection. Apply the same `useTransition` pattern there if that's ever reported as still feeling frozen.
