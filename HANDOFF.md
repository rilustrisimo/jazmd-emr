# Handoff — Gorne MD EMR

Read this first in any new session working on this project. It exists because this project was scaffolded from a Claude Code session rooted at a *different* directory (`~/Sites/jazgornemd.com/jazgornemd-theme`), so file edits were happening one directory over from the session root — annoying enough that we're picking this up fresh, rooted directly at `~/Sites/gorne-md-emr`, from here on.

## What this project is

A ground-up replacement for a WordPress-based clinic EMR (`jazgornemd-theme`, at `~/Sites/jazgornemd.com/jazgornemd-theme`) built for a small Philippine medical practice (Dr. Gorne — adult and pediatric patients, distinguished by which doctor account is logged in). The old system: patients, diagnoses, prescriptions ("resitas"), medical certificates, and vital signs stored as WordPress ACF postmeta, gated behind a login wall, with real security bugs (two AJAX endpoints leaked clinical data to unauthenticated requests) and fragile design (a `doctor` role referenced everywhere but never defined in code, patient adult/pedia segmentation hardcoded to doctor email addresses).

A full audit of that old system was published as an artifact: **"JazGorneMD Chart Review"** (`https://claude.ai/code/artifact/28e8b370-8de4-468c-9b8d-eba747998bd1`) — it documents every field, workflow, role, and security finding of the old app, plus a "Exporting to a new system" section covering WordPress data migration (deferred to a later phase — not part of this build).

## The full architecture plan

**Read `/Users/eyorsogood/.claude/plans/lets-check-and-review-graceful-rabin.md` in full before continuing implementation.** That plan file (outside this repo, on the machine this was built on) is the source of truth for: the Supabase schema and RLS design, the auth/role model, signature capture design, the PDF generation approach and why it was chosen over alternatives, the "seamless issuing" UX flow, and the full phased roadmap. What follows here is only a progress checkpoint, not a replacement for that plan.

Key decisions already made (do not re-litigate these without a good reason):
- **Separate, dedicated project** — intentionally not merged into the user's other, larger `clinic-management` monorepo (different clinic, has appointments/visits/labs/billing/inventory/Loyverse POS, no prescriptions/med-cert features of its own).
- **Scope**: patients, vitals, diagnosis, prescriptions, medcerts only. No appointments, billing, inventory, or visit/queue/encounter concept. Prescriptions/medcerts stand alone directly against the patient chart.
- **Roles: `admin` and `doctor` only** (no third "staff" role). Admin = non-clinical superuser (data management, account provisioning). Doctor = clinical role, owns a signature, issues prescriptions/medcerts under their own name. Both can view/manage patients, vitals, diagnosis; only `doctor` can create new prescriptions/medcerts.
- **Print target**: half-letter Rx pad, placeholder 139.7mm × 215.9mm in `lib/print/page-size.ts` — **must be confirmed against the actual physical pad with a ruler before launch**, that file is the only place the dimension is defined.
- **PDF approach**: `puppeteer-core` + `@sparticuz/chromium` in a Vercel Node.js serverless function, sharing one HTML/CSS template with the browser-print route. Implemented in Phase 3 (`lib/pdf/render.ts`) and verified working locally; the named risk (does it actually fit Vercel's function size/cold-start limits) is still unconfirmed for real — see Phase 3's section below.
- **Signature**: `react-signature-canvas`, captured once per doctor, stored in Supabase Storage, pinned by `signature_id` on each document at issue time (never re-resolved) so reprints stay faithful to what was signed at the time.
- **Cloud infra**: the user creates the Vercel project and Supabase project themselves — fresh instances, no reuse of any existing project. Nothing in this codebase provisions cloud accounts.
- Next.js scaffolded at **v16** (latest, not v15) deliberately — the user asked for "today's tech standards," and version parity with the sibling `clinic-management` project wasn't judged worth sacrificing that for. `AGENTS.md`/`CLAUDE.md`'s `@AGENTS.md` import is auto-generated by Next 16's own tooling (`next dev`) warning that this Next.js version has breaking changes vs. older training data — heed it, don't delete it.

No `form.tsx` wrapper — forms are built directly with React Hook Form (`register`/`Controller`) plus these primitives.

- `proxy.ts` — redirects unauthenticated requests to `/login` and authenticated requests away from `/login`, via `@supabase/ssr` on Next 16's `proxy` convention (not `middleware.ts` — deleted by the codemod, don't reintroduce it). **Note**: proxy does not handle `/` itself — `app/page.tsx` is a small server component that calls `requireUser()` and redirects to `/patients` or `/login`; it was left as the create-next-app boilerplate for a while and silently never redirected authenticated users, so don't assume proxy covers every route.

This didn't exist for a while after Phase 0 — there was no way to log out at all until it surfaced while writing an automated two-account test. Wired into the app shell's header.

### Phase 1 — Patient chart CRUD (done)

- `lib/validation/patients.ts` — `patientSchema`/`labResultSchema`. Exports **two** types from one schema: `PatientFormValues` (`z.input`, what the form holds pre-transform) and `PatientInput` (`z.output`, what gets submitted post-transform) — the empty-string-to-null transforms on optional fields make these genuinely different shapes, and treating them as one (`z.infer`) breaks TypeScript against `zodResolver`. `PatientForm.tsx` uses RHF's 3-generic `useForm<TFieldValues, TContext, TTransformedValues>` to keep both ends typed correctly — reach for this pattern again for any future form with optional/transformed fields (vitals, diagnoses, prescriptions).
- `lib/patients/age.ts` (`computeAge`, honoring `age_override` same as the plan's escape hatch), `get-patient.ts`, `get-lab-results.ts`, `types.ts` (`PatientRecord` + DB-row↔form-input mapping). `lib/storage/signed-url.ts` — every patient photo / lab-result file the UI shows goes through a short-lived signed URL minted server-side; buckets stay private, never a public bucket URL.
- `app/api/patients/route.ts` (list defaults to the logged-in doctor's `doctor_patient_scope`, `?type=all|adult|pedia` overrides; create), `app/api/patients/[id]/route.ts` (get/update/soft-delete — delete is `requireRole(['admin'])` in the route *and* backstopped by the DB trigger), `app/api/patients/[id]/photo/route.ts`, `app/api/patients/[id]/lab-results/route.ts`, `app/api/lab-results/[id]/route.ts` (admin-only delete).
- `components/patients/*` (`PatientsList` search+table, `PatientForm`/`PatientEditForm` shared form, `PatientPhotoUpload`, `LabResults`, `PatientDeleteButton` confirmation dialog) and `app/(app)/patients/{page,new,[patientId],[patientId]/edit}.tsx`. The chart page's tabs include placeholder panels for Vitals/Diagnosis (Phase 2) and Prescriptions/Med certs (Phase 3) — don't build those out until their phase.

**Verified** with an automated Playwright run against the live dev server using a real (throwaway, fully torn down afterward) doctor + admin account pair: doctor creates a patient and sees it in their scoped list; a lab result persists; editing works; admin sees the same patient with no scope restriction and has a delete control the doctor correctly does not; soft-delete removes it from lists. This is the pattern to repeat for Phase 2/3 verification — spin up throwaway accounts via the service-role key (`auth/v1/admin/users`), test, then delete them (note: deleting an auth user with `audit_log` rows referencing it fails on the FK — clear those rows first if you need to clean up a throwaway account, real accounts should never need this).

### Phase 2 — Vitals & Diagnosis (done)

- `lib/validation/{vitals,diagnoses}.ts` — same `z.input`/`z.output` split as `lib/validation/patients.ts` (`VitalSignsFormValues`/`VitalSignsInput`, `DiagnosisFormValues`/`DiagnosisInput`), for the same empty-string-to-null transform reason. Reach for this pattern for any future form with optional/transformed fields (prescriptions, medcerts).
- `app/api/patients/[id]/{vitals,diagnoses}/route.ts` (list, create) + `app/api/{vitals,diagnoses}/[id]/route.ts` (delete) — `requireUser()` only, **no** `requireRole`. Unlike patients/lab-results, the RLS policies for these two tables don't restrict delete to admin (either role can delete their own or anyone's vitals/diagnosis entries), and neither table has an *update* policy at all — records are append-only once created, so there's deliberately no PATCH/edit route for either.
- `lib/patients/get-{vitals,diagnoses}.ts` — server-side fetchers for the chart page, same shape as `get-lab-results.ts`.
- `components/records/{VitalSigns,Diagnoses}.tsx` — inline add-form + list + delete, same combined-component pattern as `components/patients/LabResults.tsx`. Wired into the chart page's Vitals/Diagnosis tabs in place of the `<ComingSoon phase="Phase 2" />` placeholders.

**Verified** the same way as Phase 1: a throwaway doctor account records vitals (BMI generated correctly: 70kg/175cm → 22.9) and a diagnosis, both persist and display. One dev-only flake hit and ruled out during testing: a brand-new API route's literal first-ever request can return a bogus 200 with an empty body — Next dev's on-demand compilation appears to double-dispatch a route's first hit before it's warm. Confirmed not a real bug (isolated direct API call and a repeat UI run were both clean, 201/no errors) — production builds compile ahead of time, so this won't occur there. If you ever see a similarly inexplicable status code that doesn't match either of a route's own return paths on a route you *just* created, suspect this before the route's own logic.

### Phase 3 — Prescriptions, Med Certs, Signature, PDF (code complete, two things blocking sign-off)

- `lib/validation/doctor-profile.ts`, `lib/doctor-profile/get-doctor-profile.ts`, `app/api/doctor-profiles/{route,[id]/route}.ts`, `components/doctor-profile/DoctorProfileForm.tsx` (letterhead fields + a `clinic_locations` repeater via `useFieldArray`), `app/(app)/settings/doctor-profile/page.tsx`. The plan's file list only mentioned GET/PATCH by id for this route; added a POST since nothing could ever get created otherwise.
- `lib/signatures/get-signature.ts`, `app/api/signatures/route.ts` (GET own active signature + signed URL; POST deactivates the previous active row then inserts the new one — `doctor_signatures` has a partial unique index, one active row per `doctor_profile_id`), `components/signature/{SignaturePad,SignatureCapture}.tsx` (`react-signature-canvas`, trims to content, exports PNG), `app/(app)/settings/signature/page.tsx` (blocks with a prompt to complete the doctor profile first if none exists — the signature insert needs an owned `doctor_profile_id`).
- `lib/documents/issuing-context.ts` — resolves the acting doctor's `doctor_profile_id` + active `signature_id`, pinned onto the document at issue time and never re-resolved (so a doctor re-signing later doesn't rewrite history on old documents, per the plan).
- `app/api/patients/[id]/{prescriptions,medcerts}/route.ts` (list, create — doctor-only, 409 with a clear message if profile/signature aren't set up yet) and `app/api/{prescriptions,medcerts}/[id]/route.ts` (get, void). Void does its own admin-or-owning-doctor check before writing — same "API route is the actual write-time enforcement, DB trigger is a backstop" pattern as everything else in this app.
- **Bug found and fixed while building void**: `supabase/migrations/0002_fix_void_trigger_service_role_writes.sql`. The original void-guard triggers on `prescriptions`/`medcerts` check `current_profile_role()`, which resolves via `auth.uid()` — null for service-role-authenticated writes, which is how every write from this app happens. The original trigger treated null as "not authorized" and unconditionally rejected every void attempt (confirmed against the live DB before fixing it: every void attempt returned `"Not permitted to void this prescription"`). Fixed to only enforce the check when a real session actually resolved a role — mirrors how the patients soft-delete trigger already no-ops on null, just making it deliberate here instead of an accident of that trigger's negated condition. **⚠️ This migration has NOT been applied to the live Supabase project as of this checkpoint — voiding a prescription or medcert will fail until it is.** Same apply-via-SQL-editor process as `0001`/the earlier fix.
- `lib/print/document-styles.ts` + `lib/print/render-document-html.ts` — the shared template, deliberately plain HTML-string generation (not a React component, despite the plan's file list naming `components/print/PrescriptionDocument.tsx`) so the *exact same string* feeds both Puppeteer's `page.setContent()` and the browser-print page's `dangerouslySetInnerHTML` — zero risk of the two drifting, which was the plan's stated reason for sharing a template in the first place. `lib/documents/get-print-data.ts` fetches and shapes the joined patient/doctor/signature data, inlining the signature as a base64 data URI (never a signed/public URL, per the plan).
- `lib/pdf/render.ts` — `puppeteer-core` + `@sparticuz/chromium` when `process.env.VERCEL` is set (true on every Vercel deployment including previews), full `puppeteer` (new devDependency) otherwise as a local stand-in only, never bundled into production.
- `app/(app)/patients/[patientId]/{prescriptions,medcerts}/[id]/print/page.tsx` (browser-print; the app shell nav is hidden via `print:hidden` on the header in `app/(app)/layout.tsx`, confirmed working with `page.emulateMedia('print')`) and `app/api/{prescriptions,medcerts}/[id]/pdf/route.ts` (`runtime = 'nodejs'`, `maxDuration = 60`).
- `components/records/{Prescriptions,Medcerts}.tsx` — issue form, list, print/download/void actions, wired into the chart page's last two tabs.

**Verified locally** (throwaway doctor account, fully torn down after — same pattern as every prior phase): doctor-profile-then-signature gating works; both document types issue with the signature correctly pinned; **both PDF endpoints were confirmed by reading the actual generated PDF bytes** — letterhead, patient info, content, and the real captured signature all present and correctly positioned on a half-letter page; the browser-print route matches the PDF exactly (same template function) and print media correctly hides the app chrome.

1. **Void is blocked** until migration `0002` above is applied.
2. **Real Vercel deployment is unconfirmed.** This session has no access to the Vercel account this project should deploy under (the CLI here is logged into an unrelated account, `thelivingpupildev` — same kind of mismatch as the Supabase CLI issue back in Phase 0). ### Password reset (done, outside the phased plan — added when the user got locked out)

- `app/(auth)/forgot-password/page.tsx` (email entry, `supabase.auth.resetPasswordForEmail()`, always shows the same "check your inbox" state regardless of whether the email is registered — avoids leaking which clinic staff emails exist) and `app/(auth)/reset-password/page.tsx` (sets the new password after the emailed link). Both added to `proxy.ts`'s `PUBLIC_PATHS`. A "Forgot password?" link was added to `app/(auth)/login/page.tsx`.
- **Real bug found and fixed while verifying this**: `@supabase/ssr`'s `createBrowserClient` hardcodes `flowType: 'pkce'`, but this project's Supabase Auth is configured to send recovery emails using the **implicit** flow (`#access_token=...&refresh_token=...` in the URL fragment, confirmed by generating and following a real recovery link). A PKCE-configured client does not auto-detect an implicit-flow fragment — `detectSessionInUrl` silently does nothing, so the reset-password page would show "invalid or expired link" for every real recovery email, permanently. Fixed in `reset-password/page.tsx` by parsing `window.location.hash` manually and calling `supabase.auth.setSession({ access_token, refresh_token })` directly, with a `getSession()` fallback for a PKCE-style (`?code=`) link in case the project's Auth flow-type setting ever changes. If you ever add magic-link sign-in or any other Supabase email-link flow, this same mismatch will bite you there too — either fix it the same way (parse the fragment, call `setSession`/`exchangeCodeForSession` explicitly) or change the project's Auth flow-type setting in the Supabase dashboard to match `@supabase/ssr`'s PKCE expectation.
- **Verified end to end against the live Supabase project**: generated a real recovery link via the admin API (`POST /auth/v1/admin/generate_link`, which returns the link directly — no need for actual email delivery, useful for testing this without an SMTP provider configured), drove it through both pages with Playwright, confirmed the new password actually works for a fresh login afterward. Also verified the always-succeeds forgot-password messaging and the invalid-link state with no token present.
- The user's real admin account (Jasmin Gorne) password was reset directly via the service-role key during this work, at their explicit request (they were locked out) — a one-off action, not part of the code change.
